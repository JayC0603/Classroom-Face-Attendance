# Webcam comparison with registered photos

The requested default flow is webcam -> compare with registered face images ->
show a name/student ID on the camera card. No manual feature vectors, FAISS index,
YOLO deployment or AdaFace upload is required. SFace computes private features
inside its adapter; images are not compared as raw pixels.

## Root cause of the old model errors

The existing `Postgres Validation YOLO / validation-v4` artifact is a 142-byte
controlled test graph with input/output `[1,3,8,8]`, not a person detector. Its
manifest cannot satisfy the production YOLO adapter. SCRFD/AdaFace definitions
have no uploaded versions. These historical custom deployments are retained;
they are not falsely marked healthy or relabeled as SFace models.

Default model UI now reports the actual YuNet/SFace service. The custom pipeline
and its original readiness are available in a collapsed advanced section.
The worker can supply frames without a person detector; that capture-only status
is distinguished from errors in the new comparison engine.

## Runtime and bounds

- Registered originals remain PostgreSQL-backed enrollment records and explicit
  image files. Latest five images per active person are considered, up to 200
  people. Exceeding that capacity is explicit. Model features are transient,
  normalized once, and rebuilt from photos on restart/model-profile changes.
- Images need one usable face. No usable face, multiple faces, unavailable image
  and model inference failure remain separate outcomes. A failed forced rebuild
  invalidates cache freshness; comparison cannot reuse a stale successful result.
- Direct/RTSP frames use the bounded worker preview; browser webcam uses its
  existing latest-frame store. Recognition reads frames no older than three
  seconds. Requests are revision scoped, with session and freshness checks again
  after inference. Old sessions cannot return names into replacement streams.
- One comparison runs at a time, with nonblocking busy responses, bounded
  per-camera frame-result cache and verification tracks. Registration changes
  refresh within five seconds; an explicit reload rebuilds immediately.
- Cosine scores aggregate photos by person before computing the runner-up margin.
  The local starter profile uses score >=0.45, distinct-person margin >=0.05 and
  at least three consecutive distinct observations in five seconds, spanning at
  least 0.5 seconds. This is a calibration starting point, not a universal accuracy
  guarantee. Contradiction, missing face, expiry, gallery/revision/session change
  clear verification. Scores are not identity probabilities.
- Camera cards show candidate versus verified name/ID explicitly. No attendance,
  durable identity event or evidence record is generated by this observation UI.
  The recognition response can include its exact JPEG snapshot together with
  frame/session IDs and remaining freshness time. The UI renders normalized
  bounding boxes and candidate/verified name labels on that same image, with
  separate colors/text for pending, verified and unknown observations. It drops
  expired snapshots and never draws old coordinates on a newer raw preview.

## Evidence

Official models downloaded and checksum verified. Real CPU load/warmup succeeded.
The existing three registered images produce usable references for one person.
Same-reference inference returned cosine 1.0, dimension 128 and L2 norm 1.0;
this proves plumbing/self-consistency, not independent recognition accuracy.

Tests cover aggregation by identity, distinct-frame verification, contradiction,
expiry/revision reset, corrupted weights, stale gallery refusal after forced and
normal rebuild failures, active revision access, browser/worker session replacement,
bounded preview/auth and UI candidate versus verified states/cleanup.

re-enabled automatically; physical webcam matching needs Enable then Activate.

review findings about replaced sessions and failed forced-refresh cache reuse
